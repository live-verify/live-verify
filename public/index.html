What it needs next

  • First issuers. A university, a lab, a bank, a council. No organisation has adopted it yet; the first ten get direct help.
  • Owners. A standard like this belongs in committee, as the internet's protocols are at the IETF: Google, Apple, Microsoft and the others who build phones, browsers and document viewers. This project is the working draft offered to them.
  • Each country's own hierarchy. 190+ countries, and international bodies such as the UN, the WTO and Interpol, would each arrange the issuers they vouch for. Nobody runs a central list.

The £122m document nobody could check

During the pandemic, PPE Medpro supplied the NHS against a safety test report bearing Intertek's name — report code SHAT06648491. Intertek never issued it. The forgery rode through goods-inwards across 72 shipments; only much later did the UK government establish it was fake, and that finding became a pivot of its lawsuit — courts ordered £122m repaid, and the unusable goods had long since gone to landfill anyway.

If Intertek had published a hash of every genuine report on intertek.com, Medpro's own goods-inwards team could have caught the fake in four seconds, on day one — refused to accept and pay for the first shipment, and, failing that, cancelled the other 71. That gap — between a document that names an authority and a way to ask that authority — is what Live Verify closes, for every document type, in every industry.

Forgery is now free

Until recently, a convincing forged certificate took skill, software, and nerve. Today anyone can ask a chatbot for a pixel-perfect insurance certificate, bank statement, employment letter, or test report — correct letterhead, plausible reference numbers, clean typography — in under a minute, at zero cost. Every control that relies on a document looking right is already obsolete.

Detection is an arms race that defenders lose: each generation of fakes is trained against the last generation of detectors. Attestation doesn't play that game. A document either hashes to a value the issuer's own domain stands behind right now, or it doesn't — and no improvement in generative models changes that arithmetic. The organizations that adopt issuer-side verification early aren't taking a bet on a trend; they're exiting an arms race they can't win.

How it works

Documents carry a verify: line pointing at the issuer's domain, e.g. verify:issuer.example.com/claims. On screen (a PDF, web page, or email): select the text. On paper: point a phone camera at it. Either way, the text is normalized, hashed with SHA-256, and looked up at the issuer's URL. You decide whether that domain is an authority on the claim.

1
Get the text
Select it on screen, or photograph it on paper.
2
Normalize
Tidy spacing and character variants on your device, so the same text always gives the same hash.
3
SHA-256
Hash the normalized text. Only the hash leaves your device.
4
Verify
Look the hash up at the issuer's URL. Found (200) returns a status such as OK or REVOKED; not found (404) means the issuer does not stand behind this text.

The bigger picture

Taken together this is more than a product. It works the way the web and email do: an open standard anyone can implement, with no central database and no operator to trust, breach or switch off. Each country runs its own chain of issuers under its own government, and international bodies run theirs. Further out, the same check works for people at the door: a badge you can check on the spot.

What "Verified" means (and doesn't)

  • Verified means: the domain in the verify: line currently attests to the hash for the extracted text above it.
  • It is not "ground truth": the issuer can be wrong, malicious, or out-of-date.
  • The human decides whether that domain is an authority for the claim in question.
  • Look out for lookalike/typosquatted domains: while much of verification is automated the domain should be shown prominently for humans to judge or not as part of a "trust or don't trust" decision.

Verifications are revocable

Revocation is part of trust. Issuers can update or withdraw claims over time, so the result reflects what they stand behind today. Some issuers may return an operational instruction, e.g. Stolen ID — please retain/cut in half and contact https://example.com/stolen_and_found quoting reference 283762..

Privacy model

Text normalization + SHA-256 happen on-device (Clip mode never sends your text anywhere; Camera mode runs OCR on-device too). The only network step is a hash lookup. The science of one-way hashes is explained at one-way-hash.html, and we go into the rest of the guarantees in the Privacy Declaration.

Does this depend on one person sticking around?

No — by design. It's an open standard (Apache 2.0), publicly disclosed as unpatentable prior art, with no trademark to capture. Every verification endpoint is a static file on the issuer's own domain, not on any infrastructure this project runs. If the project stopped tomorrow, every deployed endpoint keeps answering, and anyone can carry the spec forward. That's the opposite of the usual “what if the vendor disappears?” risk.

The flip side of being unpatentable: there's no exclusivity to sell, and no licence fees to collect — so there's no obvious way for the work to fund itself. If you find this useful and can help support it somehow, that would be genuinely appreciated. Get in touch.
